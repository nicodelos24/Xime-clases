## 1. Preparación y criterio de evidencia

Fixtures exclusivamente sintéticos: institutos A y B con alumno, clase, ciclo, pago, archivo y aviso cada uno; dueños A1/A2 en A y B1 en B; usuario M con membresías A/B de permisos distintos para pruebas futuras; usuario sin membresía; usuario/membresía deshabilitados; sesiones `aal1` y `aal2`. Incorporar roles futuros como casos denegados, sin habilitarlos en el piloto. Reloj servidor controlado, casos Montevideo del PLAN y fallos de red/concurrencia inyectables.

Para cada superficie expuesta, probar tanto operación legítima como adversarial: Data API directa (no solo UI), RPC, funciones, joins/reportes, Storage, Realtime y workers. Probar lectura, inserción, actualización de campos/tenant/FK y borrado; si no existe una superficie, documentar evidencia de que está deshabilitada. Incluir conteos, paginación y respuestas de error; no basta que la pantalla quede vacía.

Por caso, Gino debe guardar: ID SEC, commit candidato y huella de configuración/migraciones, entorno, actor/tenant/MFA, request o comando reproducible sanitizado, resultado esperado/real, estado BD antes/después, veredicto y ruta de evidencia. Nunca adjuntar JWT/refresh, contraseñas, secretos o datos reales. Las pruebas deben confirmar que **sí hay datos esperados para un autorizado**: un resultado vacío para todos no demuestra aislamiento correcto.

Denegación válida: 401/403, ausencia de filas permitida por contrato o error de autorización estable, sin revelar existencia ni contenido ajeno; para toda escritura fallida, cero cambios de negocio/auditoría financiera. No confundir 500 accidental con autorización correcta. Los intentos de seguridad pueden quedar en un canal separado. Para revocación usar un access JWT aún no vencido y el siguiente request posterior a revocación confirmada.
